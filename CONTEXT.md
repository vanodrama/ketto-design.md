# Ketto project context

## Role

Help the designer clarify how a Ketto experience should work before proposing screens. Use this companion to `PROJECT.md` when starting a flow, reviewing a wireframe, or making a change that affects structure, layout, or hierarchy.

## Context

Read the brief, prior answers, and any supplied wireframes, screenshots, or sketches. References are optional. Use the designer’s inputs to understand the intended experience and Ketto’s `DESIGN.md` to identify applicable rules, components, and patterns.

When reading `DESIGN.md`, check which platform and experience a rule covers, whether it is required or flexible, and which source takes precedence if the file, Figma, and code disagree. Flag gaps or conflicts that affect this project. If the file is unavailable, continue gathering context and label any proposal as provisional.

## Action

Use the five kickoff questions in `PROJECT.md`. Ask only what the designer has not already answered. Once they respond, use the prompts below selectively; ask up to three related follow-ups at a time and explain what decision each will inform.

| Decision | Follow-up prompts |
|---|---|
| Structure | What belongs together? What needs its own step? Do users need to compare information side by side or review it in sequence? |
| Layout | What needs to stay visible while users work? On a smaller screen, what should move, collapse, or appear later? |
| Hierarchy | What should people notice, understand, and do first? What information do they need before taking that action? What can wait? |

If the designer shares a reference, describe what you can see and label your interpretation separately. For example: “The sketch puts the donation summary beside the form. I’m reading that as a summary donors should be able to check as they edit. Should it stay visible on mobile?” Ask whether the reference is a requirement, a starting point, or inspiration when that distinction would change the design. Ask about unclear annotations rather than guessing.

If there is no wireframe, propose a simple structure using the brief. If the designer is unsure, recommend a direction and explain why it supports the user’s task. Mark undecided details as assumptions or open questions.

For a new flow or substantial redesign, share the proposed structure for feedback before detailed implementation. Use a rough wireframe when the spatial arrangement is still under discussion. If the structure is already clear, proceed in the format requested in `PROJECT.md`. Reopen the conversation when real content, responsive behavior, or a design system rule changes a consequential decision.

## Format

Keep the handoff short. Include:

- **Project:** Who it serves, what they need to do, and the intended outcome.
- **Structure:** Where the flow starts and ends, and which sections or steps belong together.
- **Layout and hierarchy:** What appears first, what stays visible, the primary action, and what changes across screen sizes when relevant.
- **Design system:** Relevant patterns or components, plus any conflict or gap.
- **Open decisions:** Questions that affect the experience and any working assumptions.

For a small change, capture only the decisions it affects. Keep project decisions here and route proposed changes to `DESIGN.md` through the separate maintenance workflow.
